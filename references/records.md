# Structural audit records

The helper requires Python 3.12 or later and is optional for small prose tasks. It validates provenance and edit integrity, not correctness of judgment. Run it against explicit UTF-8 source/export files. Offsets are Unicode character offsets in the decoded file with line endings preserved; source SHA-256 is over raw bytes. It splits nonempty paragraph blocks, not sentences. A reader must inspect every word in each block; tables/formulas and rendering need their own native inspection. Binary artifacts are hashed separately, with no inferred text coverage.

`snapshot` refuses an existing output, freezes source hashes and text units, and optionally hashes binary `--artifacts`. Inputs named with `--files` are audited prose and require reader rows. Use `--evidence` for supporting UTF-8 data, code or logs: their hashes and cited ranges are checked, but they create no reader rows and cannot be edited as prose. Evidence-only files are copied unchanged into scratch output. Pass `--generated FILE ...` to mark inventoried prose outputs that must not be staged as editable inputs. A narrowly anchored comment-header warning also rejects generated inputs; incidental prose about data "generated by" a simulator does not. Paths resolve inside the project root; symlinks are rejected. Inputs must be UTF-8 (a BOM is allowed and preserved). Do not snapshot only an extract and call it coverage of the source PDF.

Review record (empty edits are allowed):

```json
{
  "snapshot_sha256": "SHA256_OF_SNAPSHOT_FILE",
  "coverage": {
    "inventory_scope": "Named source files and export provenance",
    "rendered": "not_checked: no PDF supplied",
    "evidence": "Opened facts.txt, verified population and units",
    "derived": "not_applicable: standalone abstract"
  },
  "rows": [
    {"id": "U00001", "quote": "Exact complete unit text", "verdict": "ok", "assessment": "What this unit establishes and why its wording holds"}
  ],
  "edits": [
    {
      "id": "E1", "source": "abstract.md", "source_sha256": "RAW_FILE_HASH",
      "start": 0, "end": 38, "current": "Exact source span", "proposed": "Exact proposed replacement",
      "reason": "Specific reader harm and benefit", "declarations": [],
      "meaning": {"status": "preserved", "assessment": "Actor, comparator, scope and uncertainty remain the same"},
      "evidence": []
    }
  ],
  "required_checks": [{"name": "compile", "status": "passed", "receipt": "Command, actual exit code and newly built artifact"}]
}
```

Use real spans rather than the illustrative offsets above. Every unit requires exactly one row; verdict is `ok`, `finding` or `question`; an assessment is required. A question may remain in a valid structural record, but must be disclosed in the actual report. Edit `meaning.status` is `preserved` or `changed`. Declare `number`, `unit`, `citation`, `scope`, `strength` or `term` where applicable. The helper detects only some numeric/citation/quantifier/unit tokens; short symbols such as `s` and `us` require a numeric prefix so ordinary possessives/pronouns are not mistaken for units. Bare symbolic labels and contextual ambiguities (such as a decade ending in `s`) still require reader judgment, as do all other semantic changes. It will not prove that declarations are complete.

Token checks inspect the complete source before and after each edit, applied from right to left so original offsets remain valid and neighboring edits are checked together. Selecting only `ms` in `12 ms`, a digit within a number, a citation key, or a contraction suffix does not remove its surrounding context. Number, citation and unit token order remains significant. These scans are heuristics, not a parser or semantic proof; units outside the recognized set and assertions that change without changing monitored tokens still need reader judgment.

Strength tokens ignore capitalization and straight/curly apostrophe typography. Reordering the same strength tokens still raises an alert: moving negation or a quantifier can change scope. After actually checking the actor, modality, conditions and negation/quantifier scope, acknowledge a meaning-preserving reorder with `declarations: ["strength"]`, `meaning.status: "preserved"`, and a specific explanation in `meaning.assessment`. That order-only acknowledgement does not require scientific support evidence. Added, removed or substituted strength tokens, a declared scope change, and every edit labelled `meaning.status: "changed"` still require mapped support. A false preserved-meaning assessment can pass; the helper does not decide whether the reader's scope judgment is correct.

Each evidence entry is an object with `source`, `sha256`, one-based inclusive `line_start`/`line_end`, `quote`, `relation` (`supports`, `contradicts`, `context`) and `assessment` explaining the specific inference. Sources must have been included in the snapshot; exact quotes must occur in the named line range, preserving original terminators when a quote crosses lines. Lines are separated by CRLF, LF or CR; Unicode paragraph separators inside a log field do not increment the line number. Changed-meaning edits require at least one `supports` entry and an explanation. This is an attestation, not a semantic theorem. A deceptive or mistaken support statement can still pass.

`required_checks` contains only checks required before the requested next action. A named check must be `passed` or `not_applicable`, with a receipt explaining the result; a requested unavailable compile belongs here as `not_verified` and blocks scratch acceptance. Do not mark it not applicable just to make validation pass. Non-required future or unavailable checks can be described in coverage limits. The helper cannot verify that a receipt is truthful or that every necessary check was listed.

`stage` checks the whole record before creating any output, refuses an existing directory, maintains relative paths and verifies the staged manifest. It rejects edits to generated files declared by the caller or marked by a conventional generated-file header. It does not run compilers, edit rich formats, enforce journal limits, discover all derived copies or apply approved changes to originals. Use the actual project workflow for those actions and preserve its evidence separately.
